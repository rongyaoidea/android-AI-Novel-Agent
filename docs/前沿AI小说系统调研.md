## 一、结论速览（12 条）

1. **范式已收敛**为「层级规划 → 逐章/逐段写作 → 修订与一致性检查」三段式；分歧只在规划粒度（段/章/卷/事件）与计划是否**滚动更新**。【论】
2. **「一次性全书规划」被三线一致否定**：提前透支情节、提前完结、重复升级、注水；论文侧给出机制解释（计划必须随写作重注入；固定「先大纲后写作」丧失适应性），工程侧给出实测（300+ 章时大纲空洞、节奏像赶进度）。【论】【工】
3. **单次输出长度天花板是系统现象**：HelloBench 实测多数 LLM 写不过 4000 词，WritingBench 观察到输出普遍卡在 ~3000 tokens；LongWriter 证明这是**对齐/数据问题**，解法是「把每段字数预算写进计划的叶子节点」再逐段生成（AgentWrite）。【论】
4. **一致性已形成五层工具箱**：规划层（细纲/事件关系）→ 检索层（RAG/KG）→ 状态层（实体/物品/叙事状态）→ 校验层（矛盾检测/符号状态）→ 修订层（重排/受控编辑/局部修复）。2025–2026 的新增量集中在**生成中的符号状态校验**（ConWriter）与**叙事状态跟踪**（NstAgent，10 万词级质量不降）。【论】
5. **节奏控制最可落地的是 CONCOCT 思路**（EMNLP Findings 2023）：用「具体度评估器」控制大纲展开顺序与过滤，57% 人评节奏更一致；工程侧对应「钩子类型序列 + 事件冷却 + 节奏规划卡」。【论】【工】
6. **「章末钩子检测 / 追读率预测」是公开研究空白**（数据私有）：目前没有把追读率当训练信号的公开论文，也没有断章检测论文——谁先做出「hook 分类器 + 留存代理指标」，谁就有差异化。【论】
7. **产品侧头部全是「逐章/逐场景 + 人看管 + 状态库」**：Sudowrite Story Engine、Novelcrafter Codex、阅文妙笔通鉴、七猫本地 Agent；「一键生成整本」的 Squibler 口碑崩塌（Trustpilot 2.3/5）。【产】【测】
8. **平台在重手治理「批量铺量」**：番茄 2026 年单月拒签 AI 低质书 10–16 万本、起点把 27 本均订过万作品撤榜、晋江只允许「校对/要素/粗纲」三级 AI 辅助。「一键成书冲签约」被证伪；**合规留痕（原稿/版本）与去 AI 味成刚需**。【产】【媒】
9. **开源工程共识**：扁平事实层 + 滚动/分阶段规划（「每 50 章细纲」或「卷骨架 + 按弧展开」）+ 结构化 verdict（含受影响章节）+ **确定性统计做门禁、LLM 只做裁定/排序**。【工】
10. **成本工程三件套**：按任务分模型（正文用便宜模型）、prompt 前缀稳定（吃缓存）、结构化压缩优先于 LLM 摘要（零 token）。CJK token 估算要修正（runes×1.5，不是 bytes/4）。【工】
11. **对我们的两条最直接动作**：规划窗口滚动化（10 章级，取消「一次最多 50 章」）；章纲加**钩子类型 / 强度**字段 + 节奏预检（连续平路、同型强钩连发）。
12. **我们已有的优势不要丢**：章节版本历史 + AI 自愈复原、双层审校生命周期（open/fixed/is_new/stale + 引用失效）、开工巡检、断点续跑、零依赖单机（Android）——调研中未发现第二个把「版本存档 + 自动复原」做成用户可见能力的系统。

## 二、论文线要点

### 2.1 基础系统（三篇定骨架）

| 系统（venue） | 规划粒度 | 关键机制 | 量化 |
|---|---|---|---|
| Re3（EMNLP 2022） | 单层 outline，逐点推进 | 计划+状态**递归重注入**（相关上下文/近期摘要/当前大纲）；DPR 检索；双重排器；角色属性字典 + 受控编辑修补矛盾 | 对 GPT-3 基线：整体连贯 +14%、切题 +20%；83%/80% 被评为人写 |
| DOC（ACL 2023） | 3 级细纲 | **细纲控制器**强制逐段对齐 + 控制强度递增 + 注入未来上下文 | 对 Re3：连贯 +22.5%、大纲相关 +28.2%、有趣 +20.7% |
| CONCOCT（EMNLP Findings 2023） | 层级大纲（最模糊优先扩展） | **具体度评估器**控制大纲展开顺序与过滤=节奏控制 | 57% 人评「节奏更一致」 |

### 2.2 长输出控制（对本项目最有价值的一条线）

- **LongWriter / AgentWrite（ICLR 2025）**：模型输出长度被 SFT 样本长度锁死——「上下文能读 100k，输出卡 2000 词」是对齐问题。AgentWrite 做法：先生成**带字数的段级计划**，再逐段生成，现成模型即可产出 >2 万词；SFT（LongWriter-6k）+ DPO 后 9B 模型在 LongBench-Write 上 84.0 分，超过 Claude 3.5 Sonnet 的 80.7。【论】
- **LongWriter-Zero（ICLR 2026 Oral）**：不依赖 SFT，纯 RL，奖励分「长度控制/写作质量/结构格式」三组 reward model。【论】
- **HelloBench（2024）/ WritingBench（NeurIPS 2025）**：横测约 30 个 LLM，多数写不过 4000 词 / 输出卡 ~3000 tokens 起重复退化。【论】
- **对项目的含义**：单章 2000–2400 字没问题（远低于天花板），但**任何「一次让模型吐 N 章内容」的设计必然截断**——规划与写作都应按小窗口切分，把字数写进章纲（本项目章纲已有 beats，可加字数预算）。

### 2.3 2025–2026 新系统（滚动规划与状态化一致性）

- **StoryWriter（CIKM'25）**：事件级大纲（事件+角色+事件间关系）→ 分配到章 → 写作时动态压缩历史。
- **WriteHERE（EMNLP 2025）**：反对固定「先大纲后写作」，把写作建模为检索/推理/写作子任务的**递归分解 + 计划执行交错**（可随时重规划）。
- **Agents' Room（ICLR 2025，DeepMind）**：4 规划 agent + 5 写作 agent（Freytag 结构）+ scratchpad；消融显示「只留规划 agent + 通用写手」反而变差——**专职写手不可省**。
- **ConWriter（2026）**：场景级增量写作 + **符号状态迁移校验** + 风险信号 + 局部修复；核心口号「在生成中控制一致性，而不是生成后评测」。
- **NstAgent（2026）**：维护结构化叙事状态（角色/过去事件/未来要求），10K→100K 词评测**质量与一致性不随长度下降**（目前公开工作唯一到 10 万词级）。
- **SCORE / KG 引导**：物品状态跟踪 + 检索式矛盾检测与修复；知识图谱作为「可编辑的世界状态」。
- **学习式规划**：Learning to Reason（2025）把「下一章规划」做成 RL 任务（奖励=续写似然提升），人评全面更优——提示词工程之外的另一条路。

### 2.4 评测生态（验收口径）

- **从通用 LLM judge 转向专用 reward model**：LitBench（EACL 2026）训练的 1B–7B RM 与人评对齐 78%，胜过最强现成 judge（Claude 3.7 Sonnet 73%）；LLM judge 有系统性**长度偏见**（EQ-Bench 用截断规避）。【论】
- **一致性基准**：ConStory-Bench / Lost in Stories（ACL Findings 2026）—— 8k–10k 词故事的五类错误（时间线/角色/事实/常识/文风）+ CED 指标，可直接借作 QA 用例清单。
- **披露效应**：读者一旦知道有 AI 参与，评价显著下降（16 组实验 / 2.7 万人）；做验收人评时必须分离「内容质量」与「来源披露偏差」。【论】

### 2.5 中文网文节奏（从业者知识，工程化程度高）

- **黄金三章**：共识是「前 3 章制造必须继续看的冲动」，但阅文官方明确「黄金章可能是前三章、前五六章，甚至第一章就够」——不是固定公式。【产】
- **追读率**：起点口径＝付费读者 24h 内读完最新章的比例，新书榜直接看它；番茄用处完读率+追读+评分驱动给量。**没有任何公开研究把它当训练信号**（数据私有）——可自建代理。【测】
- **断章钩子**：社区统计把钩型分为悬念/危机/反转/升级/世界观五类（《诡秘之主》前 30 章：悬念 47%、危机 20%、反转 13%…）；禁忌＝平淡处断、假悬念。【测】
- **字数节奏**：2000–3000 字/章是黄金区间，2000–4000 为行业惯例；日更 4000 字即超过 90% 番茄作者。【测】
- **张力研究**：Reagan 六种情感弧（EPJ 2016）；Wilmot & Keller 悬念=不确定性削减（ACL 2020）；Wattpad 实证：评论峰值出现在强叙事兴趣事件处、更新间隔本身产生悬念效应（PLOS ONE）。多用于短篇/分析，**未用于长篇网文生成控制**。

## 三、产品线要点

### 3.1 格局与治理（2025–2026）

- **三层格局**：平台内置免费 AI（阅文妙笔 / 番茄 / 七猫 / 中文在线）+ 第三方付费工具（星月 / 墨狐 / 蛙蛙 / 笔灵 / 马良等）+ Agent-Skill 新形态（SkillHub、qimao-skill 等）。国际：Sudowrite / Novelcrafter / NovelAI 三强；MidReal 已关停。【产】【媒】
- **治理时间线**：2025-09-01《人工智能生成合成内容标识办法》施行 → 各平台强制 AI 声明；2026-04 十六家平台《反洗稿自律公约》；番茄 2026 年单月拒签 10–16 万本、限制账号日月创建量、提现人脸识别；起点 2026-08 撤榜 27 本均订过万作品；晋江只允许「校对 / 要素 / 粗纲」三级。**实际口径是「禁的是低质，不是 AI」**。【媒】
- **反例**：AI 写作工具「星月写作」宣传的数十本「百万在读」爆款被番茄下架（理由「存在 AI 低质表达」），创始人群内承认「平台不想看到作者公开宣传给 AI 站台」。【媒】

### 3.2 值得关注的产品做法

| 产品 | 机制要点 | 对我们的参考 |
|---|---|---|
| 阅文妙笔通鉴（2025-10 全量） | 千万字级理解：查设定 / 找伏笔 / 算数值 / 理线索 | 我们的台账+FTS5 是同一方向；可加「问全书」检索问答 |
| 番茄 AI 工具箱 | 灵感 / 大纲 / 卡文锦囊（后续情节 5 个）/ 起名 / 扩写 / 续写 | 「卡文锦囊」式候选情节 = 写作工作台可加 |
| 七猫桌面版 | 本地保存 + 本地 Agent「在边界内使用作品知识」 | 与我们本地优先路线一致 |
| Sudowrite Story Engine | Brief→角色→beat 大纲→逐章 prose；Story Bible；单章 10–15 分钟/3000–4000 字 | 逐章节奏与「章节粘合」；实测抱怨=提前甩剧情、beat 到第 5 个以上发癫 |
| Novelcrafter Codex | 词条自动检测正文提及并链接；progressions 人物弧线随章节演进；BYOK | 「人物弧线演进」可在台账里加版本轨迹 |
| NovelAI Lorebook / AI Dungeon Memory | 关键词触发词条；自动摘要 + 向量 Memory Bank | 我们已有摘要+检索；关键词触发式注入可借鉴 |
| Squibler | 一键整书（营销） | 口碑崩：2.3/5，「改 AI 稿的时间和重写一样」——反面教材 |
| 马良写作（2026 新） | **每章后一致性检查 + 节奏分析** + 742 条样本库 | 与我们「逐章审校 + 预检」同构，验证方向 |

### 3.3 作者的真实需求（从抱怨反推）

1. 长程记忆/一致性（跨几十万字的人设、时间线、伏笔）；
2. **爽点与节奏的可控工具**（拆书学爆款、黄金三章、章末钩子、「哪些冲突不许当场解决」）；
3. 去 AI 味（保持个人文风、对抗工整/模板化）；
4. 素材与伏笔管理；
5. 合规留痕（原稿版本、AI 对话记录，应对平台审核）；
6. 多平台适配的稳定日更产能（按平台调章节长度与节奏：番茄 2200–2800、起点 3000–4500 等）；
7. 反例警示：批量铺量已被平台证伪。
- 有效混合玩法（龙空实测）：**核心设定+开篇十几章人工写，签约拿量后 AI 续写**；「喂 AI 章纲+自改，每天 1 小时 2 章」。【测】

### 4.2 设计密度最高的样本

- **novel-studio**（139★，Go，最严谨）：全书卷-弧-章骨架冻结 → 当前弧「project-all（全角色独立推演）→ 承载力校验 → seal（不可变封存）」→ 逐章渲染 + exact-body 审核；**三采样选稿**（ReaderExperienceScore 0.6 + RoughnessScore 0.4）；「承载力不足必须退回规划层，禁止靠复述/景物凑字数」；审核绑定正文 SHA-256（正文一改旧审自动失效）；作者公开过 34 小时事故复盘（SLO 12–18 分钟/章）。【工】
- **MyNovel（chinese-longnovel-skill）**：**每 50 章阶段细纲**（「模型会把 200 章目标压到前 20 章，随后只能重复升级或提前完结」）；事实锁绑定来源+正文锚点+SHA-256，**细纲与已发生事实冲突时「停」而不是偷改历史**；三级摘要（每 50 章阶段 / 每 200 章长期 / 最近 20 章）。
- **leenbj/novel-creator-skill**（684★）：每章五步门禁（记忆同步→一致性检查→风格校准→校稿→门禁脚本）；大纲锚点配额（越界即失败）；**反向刹车**（非终局章节禁止解决主线核心冲突、每章必须新增一个未解决次要问题、章末必须留钩）；**事件矩阵冷却**（冲突爽点 2 章、人物纽带 1 章、风土人情 3 章）；去 AI 味两遍式。【工】

### 4.3 一手复盘（高置信度经验）

- **xindoo 两代实践**：43 万字版暴露 5 类问题（时间线混乱、人物工具化、语言重复、爽点分布不均…）；320 章/100 万字版结论——「写成 100 章靠系统、300 章靠流程」，子 Agent 并行（每个 ≤3 章）、字数脚本 + 不达标自动重写、断点续传；坦承「不吹质量吊打人类」。【工】
- **掘金 NovelOps（2026-08）**：30 章必崩三大原因＝一致性丢失/节奏失控/套路重复 → 8 级质量门禁 + 15 条状态轨 + 270 章节奏规划卡（逐章标「憋屈连续章数 / 爽点密度 / 温度档位」）+ 计划性失控（重复触发条件→扰动动作）。【工】
- **V2EX 唐库**：3–500 万字全自动 + 摘要校验；评论区共识「能过检测不够，要过 20 年书虫的眼」。【测】

### 4.4 避坑清单（全行业踩过）

1. 不要用提示词约束流程（所有工程最终都改成**代码级护栏**：停写校验、检查点差额守卫、工具前置检查）；
2. 不要依赖「自动续跑」补丁救场（ainovel-cli 原话：唯一一次触发时 100% 没救场）；
3. 不要一次性规划全书；
4. 不要让返工范围无界扩散（重写影响评估 blast radius 是难点）；
5. 不要把重依赖（MongoDB 副本集等）作为默认安装；
6. 平台合规（AI 标注、去 AI 味、敏感词）不是可选项。

## 五、与本项目逐项对照

| 维度 | 前沿共识做法 | 本项目现状 | 判断 |
|---|---|---|---|
| 规划粒度 | 滚动/分阶段：卷骨架+按弧展开，或每 50 章细纲；拒绝一次性全书 | 单次 LLM 调用覆盖整段缺失区间，**最多 50 章**；只补缺失、不覆盖已有 | **缺口**（R1） |
| 首批与批量 | 首批小、逐批推进、可确认 | 创建首批=min(目标,50)；「继续创作」=min(50,目标)；**实测：写满 50 章后手动继续写 0 章** | **缺口**（R2） |
| 状态层 | 结构化事实层（角色/物品/伏笔/时间线） | characters/foreshadowings 台账 + 章节摘要 + 卷摘要，逐章自动回写 | 持平 |
| 检索层 | RAG/KG/BM25 混合 | FTS5 全文检索 + 最近摘要 + 卷摘要 + 台账注入 | 持平（缺 KG 可视化） |
| 生成中校验 | 符号状态校验、exact-body、时间线检测 | 写前预检（本地规则：死亡角色/重复目标）+ 逐章 LLM 审校 | 部分缺口（R6） |
| 审校与修订 | 结构化 verdict + 受影响章节 + 局部修复 + 复检 | 已具备：open/fixed/is_new/stale 生命周期、语义归并、引用失效检测、定向修复后复检、修复采纳门槛 | **领先** |
| 版本与恢复 | 快照/Saga/幂等（多为工程内部） | **每章 10 版 + pre-标签 + AI 自愈复原（本地评分）+ 断点续跑**，用户可见 | **领先** |
| 节奏控制 | 钩子类型序列 + 强度/密度 + 事件冷却 + 节奏卡 | 风格预设软基线（每章爽点/平路≤3/章末三行钩）+ 文风硬检查；**章纲无节奏字段** | **缺口**（R3） |
| 质量闸密度 | 弧末/卷末评审、多维门禁、确定性统计做门禁 | 逐章审校 + 每 10 章全局审校 + 伏笔审核 + 开工巡检；**缺卷末体检与文体统计** | 部分缺口（R5/R6） |
| 读者视角 | 留存感评分、双审核（读者档+编辑档）、WebNovelBench 类基准 | 无读者视角评分；H5 黄金三章已在路线图 | **缺口**（R7 / H5） |
| 去 AI 味 | 专用规则 + 两遍式 + 检测器对抗 | 文风硬检查（段落等长/对话占比/禁用短语）+ 预设约束 | 部分缺口（R8） |
| 成本工程 | 按任务分模型、prompt 前缀稳定、结构化压缩 | 预算护栏 + 用量统计；无模型路由/缓存前缀 | 缺口（已有 F1/H7、P1 列项） |
| 人机协作 | 授权范围推进、批确认、随时停 | staged 模式（规划后暂停）+ 停止按钮 + 巡检 | 部分缺口（R4） |
| 合规 | AI 标注、原稿/版本留痕 | 版本历史 + 本地数据（天然隐私） | 可做成卖点（H3/R9） |
| 形态 | Web 平台 / CLI / 桌面（多需服务器） | **Android 单机本地、零依赖、离线可用** | **独有** |

## 六、落地建议（R 系列，映射版本）

> 现有路线（A–H）不重复，以下为本次调研**新增**项；详见 `docs/优化与功能建议.md` 第七节。

| 编号 | 条目 | 要点 | 成本 | 依据 |
|---|---|---|---|---|
| R1 | **规划窗口滚动化** | 单次规划 ≤ `plan_window`（默认 10 章，可配）；写到窗口尾部前自动续规划下一段 | M | 论文线共识 + MyNovel/ainovel-cli |
| R2 | **批量语义修正** | 创建首批 = min(目标, 批)；「继续创作」= 已写 + 批（修 50 章封顶）；目标/批量两个概念拆开显示 | S | 实测 + Biz Studio「授权范围」 |
| R3 | **章纲节奏字段 + 节奏预检** | 章纲加 `hook_type`（悬念/危机/反转/升级/信息投放）+ `intensity`（1–5）；预检连续平路、同型强钩连发；列表/编辑器可见 | M | CONCOCT + ainovel HookHistory + leenbj 冷却 |
| R4 | 每批暂停待确认（可选开关） | 批末停「待确认」，看一眼再续；无人值守默认关 | S | Biz Studio / novel-studio |
| R5 | 卷末体检 | 卷边界（默认每 20 章）跑卷级评审：节奏曲线/爽点分布/伏笔状态/支线失踪/字数异常，输出修复项 | M | ainovel 弧末七维评审 |
| R6 | 文体统计（零 token） | 跨章重复句、章末同型、句式分布、字数异常（<60% / >180%）→ 喂全局审校 + 独立报告 | S–M | ainovel stylestat + diag |
| R7 | 读者视角评审（含黄金三章专项） | 代入感/爽点/章末牵引/信息密度 rubric 打分；1–3 章为黄金三章预设（H5 泛化） | M | novel-studio ReaderScore + WebNovelBench |
| R8 | 去 AI 味体检（两遍式） | 硬指标 + 重复句 + AI 腔清单 → 报告 + 一键润色（复用 polish 任务） | M | leenbj 两遍式 + 平台检测特征 |
| R9 | 拆书导入（P2） | 导入现成 TXT → 抽角色/伏笔/结构/文体统计，作参考或仿写基线 | L | MuMuAINovel / Long-Novel-GPT |

**推荐顺序**：R1–R3（一个版本，直接回应「50 章太快」）→ R4 + G1–G3 + H2（无人值守）→ R5–R7（质量体检）→ H3/H4 + R8 → R9。

**明确不做（调研结论）**：
1. 一次性全书规划；2. 用提示词约束流程（一律代码级护栏）；3. 重型默认依赖（保持零依赖单机）；4. 「一键铺量冲签约」定位（做质量、可控与留痕，不做铺量）。
