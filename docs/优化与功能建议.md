## 一、优化建议（现有功能的打磨）

### 1.1 创作质量（离"写得像番茄爆款"最近的一组）

## 四、决策要点（为什么是这个顺序）

- **质量 > 数量**：A1/A2 直接决定"生成的内容像不像能发的稿"，且完全本地可算，不花额外 token。
- **听书是番茄的一半读者**：E1 的投入产出比在功能建议里最高，且离线可用。
- **合规与预算**：一个防下架、一个防烧钱，都是"出事就很贵"的保险。
- **模拟器已在手**：任何 UI 级改动（B 组、E1 界面、G1 入口）都能先在模拟器验证再发版，迭代成本比之前低。

## 五、新增拓展候选（v0.8.2 代码审查后的补充，2026-10-17）

> 本节只列**上面没有的**新点子；已有条目（E1–E6 / F1–F5 / G1–G5 / B1 / C4）不重复。
> 排序依据：与「写完 → 发出去」这条最短价值链的距离 + 出事成本。

| # | 建议 | 解决什么 | 怎么做 | 量 |
|---|---|---|---|---|
| H1 | **章节版本历史与回滚** | 审校修复稿、重写、重新生成都会直接覆盖正文，覆盖错了不可恢复（代码审查两次点到「库内无版本历史」）；这是当前最大的单点数据风险 | 每次写正文前把旧稿快照进 `chapter_versions` 表（保留最近 10 版 + 来源 + 时间）；编辑器加「历史」入口可预览/回滚；纯本地零 token；顺带让「重新审校/重写」胆大一点 | M |
| H2 | **日更排期（定时自动跑批）** | 网文变现靠「日更不断」——现在自动连载只在点了之后跑，一次跑完 50 章就停；没人每天记得点 | 沿用自动连载体：设定「每天 N 章 / 每 X 小时一批」，由前台服务定时触发下一批（预算护栏 + 失败自愈不变）；配 E3 的码字统计形成「计划→执行→打卡」闭环 | M |
| H3 | **发布物料包（一键生成 + 复制）** | 发到平台不只需要正文：书名、简介、分类、标签、目录都要逐一填；现在复制只覆盖「单章正文」 | 基于已有立项数据生成：书名备选 5 个、简介 3 版（长短各一）、标签/分类建议、全书目录；一个弹层里逐项「一键复制」；纯文本零成本 | S |
| H4 | **发布进度追踪** | 用户手动粘贴到平台，时间长了分不清「写到哪」和「发到哪」，容易漏发/重发 | 工作台给每章一个「已发布」本地标记（含平台名/日期），进度条区分「已写 / 已发」；「复制下一章」直接跳未发布的第一章 | S |
| H5 | **黄金三章体检** | 番茄算法最看重开篇留存（读下去率）；前三章写砸后面全白费，而现在审校是逐章通用审查，没有「开篇专项」口径 | 复用审校 agent 加一个专项任务：按留存要素（主角登场速度、首章钩子密度、信息节奏、章末牵引）审前三章，给出逐条重写建议 + 一键按建议重写；提示词可编辑 | M |
| H6 | **读者弃书点扫描（全书）** | 逐章审校管「章内质量」，管不了「读了 30 章为什么不追了」——跳出往往因全局节奏（连续平淡章、支线迷失、主角降智） | 第二个「读者 agent」只看章节摘要链，输出「高风险章节榜 + 原因 + 修改优先级」；一次性全书扫描，成本可控；与卷摘要共用数据 | M |
| H7 | **模型降级链（主备切换）** | 现在只有重试退避，主模型整体宕机（或额度耗尽）时所有任务卡死；而作者开着自动连载期望无人值守 | 设置页为「正文/审校」各配一个备用模型，主模型连续失败达阈值自动切备用并在事件流里提示；用量按实际调用的模型记账 | S–M |
| H8 | **章节节奏曲线视图** | 数据都在本地（字数/对话比/钩子/审校数），但没有「一眼看出哪几章塌」的视图 | 工作台加折线图页签：字数、对话占比、硬伤数、回收伏笔数按章排列；点峰值跳章；纯本地统计 | S |
| H9 | **情节走向建议（卡文救援）** | 光标续写管「这一句怎么写」，管不了「接下来该发生什么」 | 基于台账 + 最近摘要，一次调用给 3 个情节走向选项（各 2 句梗概 + 影响提示），选一个作为下一章章纲雏形；卡文场景专用 | S |
| H10 | **大事记时间线** | 角色/伏笔之外，长篇最容易崩的是「时间线」（谁在何时做了什么）；现在没有这个维度 | 写后抽取阶段顺带产出「本章大事」（时间点 + 事件），汇总成大事记页；供写作注入与全书回顾；E6 关系图的可视化可复用同一套渲染 | M |

**推荐下一批（H1–H4，一个版本能做完）**

1. **H1 章节版本历史**——数据安全，出事成本最高，且是审查遗留的最大隐患；
2. **H2 日更排期**——把「自动连载」从手动工具变成真正的日更计划，直接对齐变现习惯；
3. **H3 发布物料包 + H4 发布进度追踪**——把「写完之后」的最后 20 分钟压缩成 1 分钟，S 级成本、感知最强。

其后按 H5 → H7 → H6/H8 → H9/H10 的顺序推进（H5 前移到与「黄金三章」相关的真实数据验证之后更有说服力）。

## 六、Agent 全自动化审计（v0.9.0 代码核实，2026-10-17）

> 目标：**AI 可调用所有功能、全流程无人值守**。以下按「代码事实」盘点差距并给接线方案。

### 6.1 能力 × 自动化可达性

**A 类｜已在自动流水线内（agent 自主调用，无需人工）**：立项 / 章节规划 / 逐章生成 / 文风检查+硬伤重写 / 章节审校+自动修复+复核 / 写后抽取 / 卷级摘要 / 伏笔自动审核 / 全局审校+定向修复 / AI 复原（审校处理与全局修复后自动触发）/ 预算护栏 / 停止与断点续跑。

**B 类｜API 已有、但没有任何自动触发（agent 能调、没人按）**：
单章重写 / 光标续写 / 选段修文 / 单章重新审校 / 单章抽取 / 结构调整（插删移章）/ 台账增删改 / 备份恢复 / 体检「补齐资料」（实为 UI 循环单章抽取）。→ 对无人值守而言这些是「能力存在但闭环缺失」，需按 6.2 接线或有监督 agent 决策。

**C 类｜应保留人工（合理边界）**：删除作品/章节、恢复备份（覆盖性操作）、预算与目标设定、staged 模式确认、发布到平台（合规与账号安全）。

### 6.2 无人值守的 6 个真空点（代码级）

| # | 真空点 | 代码事实 | 后果 |
|---|---|---|---|
| G1 | **批次失败不自动重试** | `spawn` 失败路径写 failed；`maybe_chain_auto` 只在成功路径被调用 | 网络/额度类失败整链停摆，auto_continue 仍显示开启，无人值守断裂 |
| G2 | **预算暂停 = 关闭自动连载** | `maybe_chain_auto` 超预算分支 `set_novel_auto_continue(false)` | 跨月不会自动恢复，需人工重开 |
| G3 | **审校处理跳过续批后无补跑** | reviewing 分支只提示并 return（auto_continue 保持 true） | 审校完成后链条悬停，等人工再点 |
| G4 | **维护巡检缺位** | 「补齐资料」仅是 UI 循环单章 `/extract`；无批量端点、无自动巡检 | 抽取失败/手工新增章节的缺摘要长期存在，影响上下文注入质量 |
| G5 | **手编章节不进自动审校** | `run_inner` 只审校本轮新写章节；`review_needs_processing` 仅在 review-all 被用 | 人工/AI 单章修改过的章节在无人值守下静默漏审 |
| G6 | **无调度器** | 自动连载只在手动启动后链式；停止/失败/达标后不再自启 | 「日更」需要每天有人点一次，这是无人值守最大的单点（H2） |

### 6.3 接线方案与优化建议

**P0｜让无人值守成立（建议并入 H2 一个版本）**
1. **失败自动重试**（G1）：run 失败后按退避自动重跑该批（默认 3 次：1/5/15 分钟；断点续跑已支持），用尽后关闭 auto_continue 并推送通知说明原因；
2. **预算待机恢复**（G2）：超预算改为「待机」状态（auto_continue 保持），下个自然月首日自动重启；发通知提示；
3. **审校后补批**（G3）：review-all / 全局审校收尾时检查「auto_continue 且未达标且未超预算 → 自动续批」，与 `maybe_chain_auto` 共用判定；
4. **开工巡检 + 批量维护端点**（G4/G5）：新增 `POST /api/novels/:id/maintenance`（缺摘要自动补 extract、空稿异常状态修正、复审「有高/中危意见且久未处理」的章节、FTS/版本自检），并在每批 run 开始前自动跑一次轻量版；
5. **H2 日更排期**（G6）：每天 N 章 / 每 X 小时一批；引擎侧定时器（前台服务存活时）+ Android WorkManager 唤醒双保险；失败/待机自动顺延而不是关闭。

**P1｜成本与可靠性**
6. **模型路由（F1）+ 备用模型降级链（H7）**：正文用强模型，规划/审校/摘要/卷摘用便宜模型；主模型连续失败自动切备用（记账按实际模型）；
7. **Prompt 缓存友好化**：把稳定不变的内容（世界观、台账、文风块）放在提示词前缀、变量放尾部——对 OpenAI/DeepSeek 一类按前缀命中的缓存可显著降本（当前 context 拼接顺序未考虑缓存命中）；
8. **全局审校增量输入**：只喂新增章节摘要 + 上一轮意见，长书每轮输入从「全书摘要」降到「增量」，成本随长度不再线性增长。

**P2｜质量上限（对齐爆款）**
9. **H5 黄金三章 + H6 弃书点**（读者视角审校，复用全局审校管线加"读者档"）；
10. **重复桥段本地检测**：新章 vs 前文按段落字符 bigram 相似度扫描（复用 `goal_similarity`），命中提示注入下一章（preflight 现只管近 5 章章纲）；
11. **监督 agent（实验开关）**：每 N 章由 LLM 决策「继续 / 重写某章 / 回滚某版本 / 调整章纲」，把 B 类的重写/回滚能力交给 AI 自主使用——这是「AI 可调用所有功能」的最终形态，建议默认关闭、按需开启并限制动作白名单与预算。

**P3｜发布闭环**
12. H3 发布物料包 + H4 发布进度追踪 + EPUB 导出（E2）。

### 6.4 结论

- **API 覆盖已完整**：A/B 类能力均有 HTTP 端点，纯前端交互（复制、草稿）本质是数据读取，无 agent 缺口；唯一建议补的是批量维护端点（6.3-4）。
- **真正缺的是「触发与恢复」**：G1–G3、G6 四个真空点让「点一次跑到目标」成立、但「长期无人值守」不成立。P0 五项做完，配合已有的人工只保留 C 类操作，即可宣称「从立项到成稿无人值守」。

## 七、前沿系统调研结论的落地项（2026-10-17）

> 依据：`docs/前沿AI小说系统调研.md`（论文 / 产品 / 开源三线）。现有条目（A–H）不重复，以下为新增项。
> 三条最重要的行业共识：① 一次性全书规划被三线一致否定（提前透支/提前完结/注水）；② 单次输出有 3–4k 词天花板，字数预算要写进计划叶子；③ 质量闸用确定性统计做门禁、LLM 只做裁定。

| 编号 | 条目 | 要点 | 成本 |
|---|---|---|---|
| R1 ✅ | **规划窗口滚动化**（v0.12.0） | 单次规划 ≤ `plan_window`（默认 10 章，可配）；写到窗口尾部前自动续规划下一段；取消「一次最多 50 章」 | M |
| R2 ✅ | **批量语义修正**（v0.12.0） | 创建首批 = min(目标, 批)；「继续创作」= 已写 + 批（修 50 章封顶）；目标与本批拆分显示 | S |
| R3 ✅ | **章纲节奏字段 + 节奏预检**（v0.12.0） | 章纲加 hook_type + intensity；预检「连续平路」「同型强钩连发」「连续高能」；章节列表 / 编辑器可见可改 | M |
| R4 | 每批暂停待确认（开关） | 批末停在「待确认」，人看一眼再续；无人值守默认关 | S |
| R5 ✅ | 卷末体检（v0.13.0） | 卷边界（每 20 章）自动跑卷级体检：强度曲线 / 爽点分布 / 钩子质量 / 伏笔逾期 / 支线失踪 / 字数异常，报告存 volume_reports，「书籍体检」查看；摘要缺失时随巡检补跑 | M |
| R6 ✅ | 文体统计（v0.13.0） | 跨章重复句（≥10 字且 ≥2 章）、章末类型单一、字数异常（<60% / >180% 中位数）、句均长；本地零 token；卷末体检提示词同步注入统计摘要 | S–M |
| R7 ✅ | 读者视角评审（v0.13.0） | 代入感 / 爽点 / 章末牵引 / 节奏 / 语言 rubric 打分；1–3 章自动叠加黄金三章专项清单（H5 并入）；书籍体检一键运行（区间 ≤20 章） | M |
| R8 | 去 AI 味体检（两遍式） | 硬指标 + 重复句 + AI 腔清单 → 报告 + 一键润色（复用 polish 任务） | M |
| R9 | 拆书导入（P2） | 导入现成 TXT → 抽角色 / 伏笔 / 结构 / 文体统计，作参考基线 | L |

**推荐顺序**：R1–R3（一个版本，直接回应「50 章太快」）→ R4 + G1–G3 + H2（无人值守）→ R5–R7（质量体检）→ H3/H4 + R8 → R9。

**明确不做**：① 一次性全书规划；② 用提示词约束流程（一律代码级护栏）；③ 重型默认依赖（保持零依赖单机）；④ 「一键铺量冲签约」定位（做质量、可控与留痕）。
